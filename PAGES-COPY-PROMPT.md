## ЧАСТЬ 6 — СИСТЕМА ТЕМ И ФУТЕР

Это не «ещё одна страница», а сквозная механика: она живёт в футере, в

Файлы: `state/themes.ts` (61 строка), `ui/pickers.ts:148-163`,
`ui/commandline.ts`, `main.ts:29-36`, `backend/app/data/themes.json` (187 тем),

### Сначала почини применение темы — без этого остальное бессмысленно

`state/themes.ts:32-54` пишет переменные темы **inline-стилями на элементе
`<html>`**. Inline-стиль сильнее любого `:root{}` из подключённого файла.
Следствия:

- css-файлы 52 тем не могут переопределить ни одну переменную;
- css-файлы funbox не могут тоже — поэтому `space_balls` не перекрашивает
  экран, а `crt` мёртв;
- любая тема применяется наполовину и **молча**.

Monkeytype вставляет `<style id="theme">` с блоком `:root{}` в `<head>`.
Сделай так же. Порядок важен: тег темы идёт **до** подключаемых css темы и
funbox. Это ~15 строк, и после них половина коллекции тем оживает.

## ГРАФИКИ — самая сложная часть, отдельное решение

У monkeytype графики на Chart.js. У нас график результата нарисован svg
вручную: одна линия wpm с заливкой.

Что нужно на экране результата: **wpm, raw пунктиром, burst, крестики
ошибок по секундам, линия рекорда, легенда из шести переключателей,
подписи оси X.**

**Решение: рисуй вручную, Chart.js не тащи.** Проект намеренно без
зависимостей, а библиотека графиков — это ~200 КБ ради одного экрана,
плюс она не знает про наши переменные тем и её придётся перекрашивать под
187 тем. Мы уже рисуем svg руками и умеем это.

Честная цена: шесть серий с легендой и крестиками ошибок — порядка 300
строк своего кода. На странице профиля добавятся ещё скорость по времени,
гистограмма и тепловая карта — считай, что графики это отдельный модуль
`ui/charts.ts`, а не куски внутри страниц.

**Блокирующее ограничение:** движок сейчас пишет только посекундный wpm.
Ни raw по секундам, ни ошибок по секундам он не хранит — рисовать нечего.
Значит сначала движок, потом график.

## ЧТО СЕРВЕР УЖЕ УМЕЕТ — начни с этого

Пять дешёвых побед, где работа только на клиенте:

1. **Пагинация профиля** — сервер принимает `offset`, клиент жёстко шлёт 25.
2. **Язык лидерборда** — параметр в API есть, кнопок нет.
3. **Вкладки 15 и 60** — сервер принимает `mode` и `mode_value`.
4. **Источник цитаты** — сервер отдаёт `source`, клиент выбрасывает.
5. **Аватар** — поле в API есть, не показывается.

## ЧТО ПОТРЕБУЕТ СЕРВЕРА И МИГРАЦИЙ

Не начинай с этого, но заложи в план:

- **личные рекорды** — новый эндпоинт. Считать на лету по таблице `Result`
  можно без новой таблицы, но при росте истории станет медленно; напиши,
  какой предел ты закладываешь.
- **тепловая карта** — агрегация по дням на сервере, иначе клиент утянет
  всю историю.
- **фильтры** — параметры валидировать на сервере.
- **теги** — новая таблица, связь многие-ко-многим, миграция БД.
- **уровень, опыт, серия дней** — новые поля в `User`, начисление при
  сохранении результата, миграция.
- **тестов начато** — сервер этого не знает; клиент должен слать событие
  старта. Реши, стоит ли лишний запрос на каждый тест.
- **настройки аккаунта** — шесть эндпоинтов, из них два трогают
  безопасность.

## ОПАСНОСТЬ — метрики

**Четыре счётчика символов на экране результата и raw по секундам на
графике требуют правок в движке.** А формулы у нас продублированы: клиент
считает для показа, сервер — для сохранения.

Правило проекта: **меняешь формулу — меняй одновременно в
`frontend/src/core/metrics.ts` и `backend/app/services/metrics.py`.**
Иначе показанные цифры разойдутся с сохранёнными, и это обнаружится не
сразу.

Есть тесты, которые стерегут расчёты — в прошлой версии `consistency` был
случайным числом. **Не ослабляй их.** Если тест мешает — значит правка
неверна, а не тест.
